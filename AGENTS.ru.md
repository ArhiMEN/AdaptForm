# Инструкции для агентов репозитория

[English](AGENTS.md) · [Русский](AGENTS.ru.md)

## Безопасность и область работы

- Никогда не удалять репозиторий, а также существующие ветки Git; не переименовывать их и не обновлять принудительно. Не переписывать общую историю и не выполнять force-push.
- Работать в текущей ветке задачи, если пользователь не запросил другую. Сохранять посторонние и уже добавленные в индекс изменения.
- Не публиковать пакет в npm, не создавать релиз или тег и не менять опубликованную версию без явного разрешения. Скрипт `prepublishOnly` собирает пакет; не использовать `npm publish` для проверки.
- Ограничивать изменения задачей. Перед изменением публичных контрактов или необратимыми внешними действиями запросить согласование.

## Карта проекта

- AdaptForm — библиотека валидации на TypeScript. Публичные точки входа: `src/index.ts` и `src/luxon.ts`; реализация находится в `src/core/`.
- `luxon` — необязательная peer-зависимость. Основная точка входа не должна зависеть от неё. Сборка создаёт ESM, CommonJS и декларации типов в `dist/`.
- Тесты находятся в `tests/unit/`, `tests/integration/` и `tests/demo/`. Интерактивная демонстрация находится в `demo/` и импортирует исходный код библиотеки.
- Проверки пакета находятся в `scripts/`, CI — в `.github/workflows/ci.yml`. Обращаться к `docs/roadmap/v2.1.0/` при работе над выпуском или изменении состояния направления работ.

## Реализация

- Перед изменением найти существующую реализацию поведения. Использовать или улучшать её вместо дублирования бизнес-логики и валидации.
- Делать публичный API явным и типобезопасным; избегать `any`, если подходит безопасный generic или `unknown`. Сохранять обратную совместимость, если пользователь не одобрил несовместимое изменение; описывать неизбежные изменения и миграцию.
- Сохранять существующие пользовательские сообщения валидации и ошибок, а также публичные имена типов, если пользователь явно не согласовал изменение контракта и план миграции.
- Добавлять или обновлять регрессионные тесты для исправлений и значимых изменений поведения. Изменения документации и конфигурации агентов не требуют поведенческих тестов.

## Язык и документация

- Писать комментарии в коде, описания тестов и примеры на английском. Синхронизировать английскую документацию с полными русскими версиями (`*.ru.md`). Сохранять пользовательские и языконезависимые значения.

## Проверка и завершение

- Начинать с нужного файла Vitest: `npx vitest run <test-file>`. При изменениях нескольких модулей или публичного поведения расширять проверку до `npm test`.
- Для затронутого кода запускать подходящие проверки: `npm run lint`, `npm run build`, `npx tsc --noEmit -p tsconfig.json`, `npm run check:package`; для демонстрации также `npm run check:demo` и `npm run build:demo`. При необходимости проверять покрытие через `npm run test:coverage`. CI дополнительно запускает `npm audit --audit-level=moderate`.
- Не сообщать об успешной проверке, если она не была запущена и её результат не был изучен. Указывать невыполненные проверки и известные ограничения.
- Для работ по выпуску v2.1.0 обновлять `docs/roadmap/v2.1.0/STATUS.md` и `STATUS.ru.md` при изменении состояния направления работ, записывая выполненные проверки и ограничения.
- Перед завершением просматривать diff на случайные изменения, дублирование логики, отсутствующие тесты и расхождение языковых версий. Если задача включает коммит, делать небольшие обозримые коммиты с описательными сообщениями на английском, не добавляя посторонние изменения из индекса.
