# HF-015 — структурированные ошибки валидации

[English](HEADLESS_ERRORS.md) · [Русский](HEADLESS_ERRORS.ru.md)

Реализовано в `hf-015-structured-validation-errors` от master `b9051dd` (HF-011: PR #25, производительность: PR #26, HF-013: PR #27). Версия пакета остаётся **2.2.0**; изменение исходников не публикует пакет. HF-014, HF-016 и HF-017 исключены.

## Архитектура и решение о совместимости

Раньше Field и коллекции хранили изменяемый `string[]`, а Form — одно глобальное сообщение на ключ. `allErrors` объединял ошибки вложенных форм с позиционными подписями; ошибки элементов обычных коллекций были доступны только на самих элементах. `ErrorsSchema.parseErrors()` и `parseErrorsDetailed()` возвращали одну запись на поле: последующий совпавший ключ заменял предыдущий. Трансформеры могли выбирать/объединять сообщения массивов. Валидация останавливается при ошибках обязательности, приведения или типа до пользовательского callback. Эти старые контракты сохраняются.

Внутренний источник истины — упорядоченный список ошибок с общим фасадом массива строк. Явные операции библиотеки обновляют оба представления. При публичном чтении согласуются внешние изменения старых массивов ошибок: совпавшие метаданные сохраняются, новые строки получают `external`. Изменения одинаковых сообщений не позволяют определить, какой дубликат имел в виду пользователь: сначала сохраняются метаданные той же позиции, затем первой неиспользованной совпавшей записи. Proxy и автоматические уведомления о произвольных изменениях на месте не добавляются. Защищённый `_errors: string[]` Field/ArrayField остаётся свойством для подклассов.

Новый серверный импорт выделен в дополнительный метод: незаметное переосмысление старых массивов или изменение маршрутизации обычных коллекций нарушило бы совместимость. `form.errors = response` по-прежнему вызывает настроенный `parseErrors()`. Новый `form.setErrors(response)` вызывает `parseValidationErrors()`; эти способы не меняют поведение друг друга. Переопределённый `parseErrors()` остаётся приоритетным через мост совместимости: уже потерянные в переопределении данные восстановить невозможно. Отложенных изменений поведения, требующих согласования миграции, нет.

## Модель

```ts
interface ValidationErrorInput {
  readonly code: string;
  readonly message?: string;
  readonly params?: Readonly<Record<string, unknown>>;
}
interface ValidationError extends ValidationErrorInput {
  readonly path: readonly (string | number)[];
  readonly source: 'client' | 'custom' | 'server' | 'external';
}
```

Код непустой. Валидаторы передают code/message/params; источник и принадлежность назначает движок. `client` означает обязательность, приведение или проверки FieldType, `custom` — callback `validate` из options, `server` — любой серверный вход Form, `external` — ручной `error`/`setErrors()` или новые строки при обнаружении внешних изменений. Старые строковые реализации FieldType получают общий код `custom` с источником `client`; для точных кодов можно переопределить дополнительный `validateErrors(value, form?)`. Подклассы встроенных типов с переопределённым старым `validate()` продолжают выполнять это переопределение.

Ошибки, пути, параметры и возвращаемые списки неизменяемы. Параметры отделяются через преобразование данных snapshot: Date/RegExp/Map/Set/бинарные данные становятся неизменяемыми описаниями; неподдерживаемые классы/функции — непрозрачными описаниями. Циклы поддерживаются, но требуют политики приложения для JSON-сериализации. Из входной ошибки копируются только code/message/params/path/source; значения полей, исходный ввод и произвольные дополнительные свойства автоматически не прикладываются. Приложение должно избегать секретов в собственных сообщениях/параметрах.

Ошибки не индексируются кодом: дубликаты и порядок сохраняются. Машинные коды не зависят от языка сообщения. `message` может отсутствовать: тогда старое строковое представление показывает `code`. Явное пустое сообщение остаётся пустым и всё равно означает ошибку нового структурированного правила. Переводы, отображение и UI-зависимости не требуются.

## Чтение и запись

```ts
import {Field, Form, StringType} from 'adaptform';

class Registration extends Form {
  email = new Field(StringType, null, {
    validate: (value: string) => {
      const errors = [];
      if (value.length < 2) {
        errors.push({code: 'min_length', message: 'Minimum length is 2', params: {min: 2}});
      }
      if (!value.includes('@')) {
        errors.push({code: 'email_format', message: 'Use an email address'});
      }
      return errors.length ? errors : true;
    },
  });
}
const form = new Registration();
form.email.rawValue = 'x';
for (const error of form.email.getErrors()) {
  console.log(error.code, error.message, error.params, error.source); // Local path: []
}
console.log(form.getErrors()); // Paths: ['email']
console.log(form.email.errors, form.allErrors); // Existing string APIs
```

`Field.getErrors()` возвращает собственные ошибки. `ArrayField.getErrors()` / `ArrayFormField.getErrors()` включают сначала собственные ошибки, затем дочерние по текущим индексам. `Form.getErrors()` обходит свойства в прежнем порядке, затем добавляет собственные глобальные ошибки в порядке вставки. Пути относительны получателю: `[]` для собственной ошибки поля/коллекции, `[1]` для элемента, `['rows', 1, 'name']` от корневой Form. Пути вычисляются при чтении, не хранят устаревшие индексы или ссылки на родителей. Field и коллекции также имеют `getOwnErrors()`. Ссылочная стабильность списков структурированного чтения не гарантируется; `getSnapshot()` сохраняет прежнюю гарантию стабильности ссылки.

`field.setErrors(inputs, source = 'external')` и одноимённый метод коллекций заменяют **собственные** ошибки, сохраняя дочерние. Используется прежняя семантика ручной ошибки: непустой список означает невалидность, пустой сбрасывает результат проверки. `error = message` поддерживается. `setErrors` формы импортирует серверный ответ и отличается от локального метода поля.

Callback может вернуть `true`, `false`, строку, один `ValidationErrorInput` или readonly-массив таких ошибок. Пустой массив успешен. False использует настроенное/стандартное сообщение и код `custom`; строка сохраняется точно, включая пустую. Другие прежние результаты JavaScript сохраняют семантику успеха, если не распознаны как ошибка с непустым кодом или непустой массив только таких ошибок. Async и новый планировщик правил не добавляются. Пользовательские callback по-прежнему не выполняются после ошибок обязательности/приведения/типа; ранние выходы ограничений коллекций сохраняются.

## Встроенные коды

| Существующая проверка | Код | Параметры |
| --- | --- | --- |
| Обязательность / ошибка приведения | `required` / `invalid_type` | Для приведения/типа: `expected` |
| Длина строки | `min_length`, `max_length` | `min`, `max` |
| Regex строки / формат decimal | `pattern` | Нет |
| Целое число | `integer` | Нет |
| Числовые границы, включая decimal | `min_value`, `max_value` | `min`/`max`, `exclusive` |
| Ограничения разрядов decimal | `max_digits`, `decimal_places` | `max`, область разрядов `scope` (`integer` или `total`) |
| Логические ограничения | `must_be_true`, `must_be_false` | Нет |
| Границы Date/Luxon | `min_date`, `max_date` | `min`/`max`: timestamp в миллисекундах |
| Существующий диапазон года Luxon | `invalid_year` | `min: 1900`, `max: 2100` |
| Размер коллекции элементов/форм | `min_items`, `max_items` | `min`, `max` |

Для конечного числа/валидной даты используется `invalid_type`; встроенные сообщения и их настройка сохраняются. `FieldType.validate(): string[]` продолжает работать независимо от структурированных ошибок. Новых проверок коды не добавляют.

## Серверный ввод и миграция схем

```ts
// Existing responses and parsing remain unchanged.
form.errors = {email: 'Already registered'};

// Opt into multiple messages and explicit codes.
form.setErrors({
  email: [
    {code: 'already_registered', message: 'Already registered'},
    {code: 'blocked_domain', params: {expected: 'work_email'}},
  ],
});

// Ordinary string arrays also retain each message in the new importer.
form.setErrors({email: ['Already registered', 'Use a work email']});
```

Поддерживаются вложенные объекты, массивы объектов форм, точечные пути после mapping, static/dynamic rules, приоритеты, fallback, `nest()`, `forArray()`, clone/merge и трансформеры значений. Трансформеры получают целое листовое значение один раз до mapping, как раньше; выбор первого элемента намеренно отбрасывает остальные. Новый парсер считает объект с непустым строковым `code` одной ошибкой. При нескольких исходных ключах, направленных в одно поле, сохраняются все записи. `parseErrors()` / `parseErrorsDetailed()` сохраняют прежние типы и последнее значение на поле.

Для формы с коллекциями `rows` и `tags`:

```ts
form.setErrors({rows: [{name: [{code: 'required'}, {code: 'remote_rule'}]}]});
form.setErrors([
  {path: ['rows', 0, 'name'], code: 'remote_rule', message: 'Check the name'},
  {path: ['tags', 1], code: 'duplicate'},
]);
```

Явные пути устраняют неоднозначность точечных ключей и поддерживают элементы обычной коллекции. Неизвестные поля/индексы становятся глобальными ошибками на разрешающей Form; несколько глобальных ошибок сохраняются в `getErrors()` и `allErrors`. Старый `globalErrors: Record<string, string>` показывает последнее сообщение на глобальный ключ. Ручной `setGlobalError(key, message)` по-прежнему заменяет ключ в его исходной позиции. Старые глобальные строковые ключи остаются буквальными, непривязанными и не переиндексируются задним числом. Старый `allErrors` сохраняет группировку/позиционные подписи и не начинает объединять ошибки элементов обычной коллекции: используйте `.errors` элемента или `getErrors()`.

Оба серверных входа формы рекурсивно заменяют предыдущие ошибки. Источник назначается `server` независимо от входных source/path. Происхождение серверных и клиентских ошибок не выводится из текста.

## Очистка, реактивность и ограничения

Существующая политика сохранена и рекомендуется для совместимой реализации:

- Любое присваивание Field очищает ошибки, даже при том же значении и `setRawValue(value, false)`; отключённая проверка оставляет validity null. Включённая проверка заменяет ошибки текущими client/custom.
- Явная валидация заменяет ошибки посещённых узлов. `Field.checkValid()` по-прежнему не присваивает `isValid`; `checkAndSetValid()` присваивает. Выбранные зависимые поля HF-013 очищают/перестраивают ошибки без изменения touched/dirty.
- Глобальные ошибки переживают изменение значений и валидацию. Очистка — через `clearGlobalErrors()`, новый серверный ввод или reset. Структурные операции коллекций запускают существующие проверки, способные очистить посещённые серверные ошибки. Ранний выход по ограничению может оставить ошибки непосещённых потомков, как раньше. Reset очищает ошибки сохранившихся узлов, сохраняя прежние состав коллекций и цели сброса.

Сохранение серверных ошибок до изменения конкретного значения, объединение server/client между проверками или очистка глобальных ошибок при любом вводе — возможные будущие политики, **не реализованные здесь**. Каждая меняет поведение и требует отдельного согласования.

Snapshots дополняются необязательным `validationErrors` с **собственными** ошибками узла; дочерние остаются в дочерних snapshots. Это предотвращает копирование агрегированных путей на каждом предке и сохраняет совместимость структурных TypeScript-производителей snapshot. Изменение только code/source/params уведомляет наблюдателей; эквивалентное состояние сохраняет ссылку snapshot и не уведомляет. Одна мутация/batch публикует итоговое состояние один раз на затронутый узел существующим движком. Чтение snapshots не валидирует. Удалённые узлы теряют родительские подписки; идентичности HF-011 сохраняются, текущие пути отражают позиции оставшихся узлов.

Неизменившееся корневое чтение по-прежнему проверяет потомков, как в PR #26. Согласование/сравнение ошибок пропорционально их количеству на узле; агрегация — числу ошибок и длинам путей. Согласование изменённого старого массива с множеством дубликатов может быть квадратичным. Полная валидация остаётся полной, кроме уже включаемого подмножества HF-013. Нет новых runtime-зависимостей, локализации, UI-адаптеров, триггеров, async fencing, отправки, изменения версии или публикации npm.

Проверки и измеримая цена метаданных: [отчёт HF-015](../roadmap/v2.3.0/ERRORS_VERIFICATION.ru.md).
