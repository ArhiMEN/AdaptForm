# HF-012 — предложение графа зависимостей валидаторов

[English](HEADLESS_DEPENDENCIES.md) · [Русский](HEADLESS_DEPENDENCIES.ru.md)

**Статус после HF-013:** явно утверждённая более узкая реализация в исходниках поддерживает только обычные Field одной Form. См. [реализованный API, примеры и ограничения](HEADLESS_DEPENDENCIES_USAGE.ru.md). Пакет остаётся 2.2.0; новой публикации нет. Более широкое предложение ниже (коллекции, позиционные пути и прямые ссылки на узлы) не реализовано и требует отдельного утверждения. Предлагаемые ниже типы не являются текущими экспортируемыми типами.

## Основной вариант API

Добавить необязательные явные зависимости в FieldOptions, ArrayFieldOptions и ArrayFormFieldOptions. Они описывают весь контекст прохода валидации узла (isRequired, правила типа и custom validate), не только custom callback. Собственное значение target подразумевается и не должно указываться как self-dependency. Автоматического обнаружения источников нет.

```ts
// Предлагаемые типы, пока не экспортируются.
type DependencyPath = readonly (string | number)[]
interface DependencyNodeRef {
  getSnapshot(): NodeSnapshot
} // малая readonly structural reference; принадлежность проверяется в runtime
type DependencyRef =
  | {readonly path: DependencyPath; readonly scope?: 'owner' | 'root'}
  | {readonly node: DependencyNodeRef}
interface DependencyOptions {
  readonly dependsOn?: readonly DependencyRef[]
}
// Предлагаемая активация корня после инициализации полей подкласса:
// form.enableDependencies(): () => void
```

Малая structural reference принимает конкретные generic Field/Form без сравнения всей рекурсивной поверхности классов. Это только ссылка, не зависимость от snapshot; произвольные похожие объекты отклоняются runtime-проверкой принадлежности дереву. HF-013 должен подтвердить это declaration tests; нельзя возвращать рекурсию STAB-01 и использовать any как обход. Пути v1 — проверяемые в runtime tuples, не неограниченный рекурсивный генератор TypeScript. Необязательные helpers с ограниченной рекурсией можно спроектировать отдельно.

```ts
// Предложение: в 2.2.0 эти члены намеренно не компилируются.
class Checkout extends Form {
  country = new Field(StringType, 'US')
  postalCode = new Field(StringType, null, {
    dependsOn: [{path: ['country']}],
    validate: (value: string, form?: Checkout) =>
      form?.country.valueClear !== 'US' || /^\d{5}$/.test(value) || 'Use five digits',
  })
}
const form = new Checkout()
const disable = form.enableDependencies() // собрать граф без валидации и touched
form.country.rawValue = 'CA'              // проверить источник и затронутые target
form.batch(() => {
  form.country.rawValue = 'US'
  form.postalCode.rawValue = '12345'
}) // каждый выбранный валидатор один раз, на конечных значениях
// При завершении работы удалить владение графа, reverse indexes и queued work.
disable() // идемпотентно; следующие мутации используют legacy-валидацию
```

Активация явная: конструктор базового Form выполняется до инициализации полей подкласса, а нынешние связи наблюдения существуют только при подписчиках. Валидация должна работать без UI-подписок. Повторная активация одного корня возвращает тот же идемпотентный disable callback без reference counting; после disable следующая активация создаёт новый граф. Корень владеет отдельным индексом состава/зависимостей; lifetime подписок им не управляет. Пустые декларации сохраняют legacy scheduling. Один дочерний узел в двух включённых графах — configuration error; legacy sharing без графа сохраняется. Вложенные активные корни с пересекающимся владением тоже отклоняются. Конфликты проверяются до установки связей; ошибка активации ничего не устанавливает.

## Пути и HF-011

- Строковый сегмент — буквальное имя свойства, включая точки; числовой — неотрицательный целый индекс коллекции. Пустой путь, отрицательный/дробный индекс, неизвестное свойство, отсутствующий/выходящий за диапазон индекс и endpoint не-узел дают configuration error. В v1 нет wildcard, разбора dot strings, JSON Pointer, `..` и неявного преобразования.
- `scope: 'owner'` по умолчанию начинает путь в ближайшем содержащем Form. Валидатор строки может зависеть от `['price']` той же строки; move сохраняет owner и идентичность. Owner скалярного элемента ArrayField — содержащий Form, не искусственный индексный Form. `scope: 'root'` начинает путь в явно включённом корне, например `['rows', 0, 'price']`. Endpoint-коллекция означает агрегат очищенных значений и упорядоченный состав.
- Числовые пути привязываются к **текущей позиции**, не исходному объекту. После изменения состава/порядка разрешаются заново; замена источника в индексе 0 вызывает перепроверку target даже при равных значениях объектов. Callback должен читать данные с тем же позиционным смыслом.
- `{node: existingField}` — явная стабильная объектная ссылка. Следует за узлом при move внутри активного дерева; callback читает захваченный узел, не изменчивый индексный путь. Изначально узел должен принадлежать активному корню. Это отношение «тот элемент», а не «первый элемент».
- ID HF-011 идентифицируют runtime-вершины и сохраняют локальные рёбра при сдвиге индексов. Snapshot itemIds — локальные metadata, не сохраняемые сегменты путей, пользовательские ID или способ воскресить удалённый узел. SetItemsValue/setForms не сопоставляют значения. Замена создаёт новые вершины; позиционные пути перепривязываются, прямые ссылки — нет.
- Существующие dot-index server errors и сериализация сохранены. Dependency paths — отдельное типизированное представление, которое не попадает в JSON/FormData.

```ts
// Предложение зависимостей валидатора строки:
dependsOn: [
  {path: ['price']},                         // локальный owner, переживает move
  {path: ['taxRate'], scope: 'root'},
  {path: ['rows', 0, 'price'], scope: 'root'}, // текущая первая строка
]
// Стабильная связь между строками (target создаётся после referencedField):
dependsOn: [{node: referencedField}]
// Валидатор замыкает referencedField и читает его valueClear.
```

## Граф, циклы и детерминированный порядок

Ребро source → target означает, что изменение source инвалидирует валидацию target. Проход проверяет весь синхронный pipeline target с сохранением текущего порядка правил и сообщений. Для агрегатных зависимостей коллекций индексируется также containment; зависимость от агрегата, содержащего сам target, является self/cyclic и отклоняется. Изменение validation metadata не становится новым источником значений; зависимости от errors/isValid/isTouched/isDirty вне v1. Валидаторы читают только объявленные cleaned values/состав коллекций; собственная raw/clean-валидация сохранена.

Перед callbacks разрешить и дедуплицировать рёбра. SCC или эквивалентный DFS отклоняет self edges и все циклы нескольких узлов с детерминированными текущими путями и ID в configuration diagnostic, без raw values. Нет fixed-point iteration, молчаливого удаления рёбер и произвольного разрыва циклов. Проверять после активации, обновления dependency options и структурной перепривязки, включая цикл из-за позиционного move.

На validation commit взять достижимое по исходящим зависимостям замыкание изменённых источников, запросивших валидацию, включая обычную проверку самих источников. Выполнять стабильную топологическую сортировку; независимые узлы упорядочивать текущим обходом корня (порядок полей, затем индексы), не порядком выделения ID. Цепочка A → B → C выполняет A, B, C по разу; ромб A → B/C → D выполняет A, B, C, D по разу (либо C перед B согласно порядку обхода), D только после обоих. Обычный false/string не останавливает независимые/зависимые проверки: все значения уже конечные. Невалидный upstream не пропускает target; тот может явно отвергать null/invalid source. Транзитивное замыкание консервативно, хотя чистые валидаторы не меняют cleaned values. Посторонние валидаторы не запускаются, кроме неизбежных существующих constructor checks и явно запрошенного полного Form.checkValid().

Публичный `Form.checkValid()` остаётся полной проверкой в существующем порядке обхода; явные проверки поля/коллекции немедленны и локальны. Selective scheduling относится только к автоматической валидации активного графа. Явная проверка не превращается в graph request. Политики показа ошибок/onBlur/onSubmit (HF-014) и async fencing (HF-016) не вводятся.

## Batch, удаление и ошибки выполнения

1. В синхронном batch собирать записи, запросы валидации и структурные изменения. Дедуплицировать запросы по стабильной идентичности target. `validate: false` / force_check false не создают автоматический graph request. Более ранний true request того же batch всё равно проверяет конечное значение, как существующая очередь. Источник с подавленной проверкой обновляет состав/привязки графа, но сам не запускает валидацию. Другой автоматический запрос может выбрать его валидатор через реальное dependency edge.
2. После всех записей: сверить конечный состав, разрешить пути, найти циклы, вычислить замыкание и проверить конечные значения. Записи с возвратом к прежнему cleaned value не требуют dependent checks; ожидающий прямой запрос всё равно выполняется. Перестановка/замена идентичности — структурное изменение и при равном содержимом. Вложенные batch объединяются во внешний проход. Constructor checks новых элементов сохраняют прежнее поведение; будущий граф не обещает их дедуплицировать.
3. Commit конечных snapshots предшествует callbacks подписчиков. Мутация подписчика начинает следующую транзакцию, не меняет текущую доставку. Чтение snapshot не запускает валидаторы. Внешние мутации legacy-массивов/custom objects не поддерживают автоматическое dependency scheduling; нужны методы библиотеки.
4. Удаление target освобождает его входящие/исходящие graph indexes и queued validation. Удаление source однократно инвалидирует оставшиеся target; локальный target, удалённый в том же batch, не запускается. Позиционные пути разрешаются по конечному составу; существующий слот получает текущий узел. Неразрешённый путь и удалённая прямая ссылка — configuration error, не пустое значение и не обычная validation error. Прямая ссылка не может молча указывать на замену: приложение должно заменить options до восстановления валидного графа. Временное отсутствие слота, восстановленного внутри batch, оценивается только при finalization.
5. Configuration errors выбрасывают предлагаемый DependencyConfigurationError до выполнения graph validators. Динамические записи уже выполнены, rollback нет. Сохранить записи, завершить уведомления, отметить граф невалидным и требовать успешной пересборки до любой следующей graph validation, включая полную проверку. Искусственные field/global errors не внедряются. После перехваченного configuration exception одного `isValid` недостаточно для подтверждения корректной конфигурации. При ошибке активации граф ещё не установлен. Владелец должен утвердить эту fail-closed политику и diagnostics API.
6. Исключение пользовательского callback сохраняет записи и выполняет finalization один раз; исходная ошибка callback приоритетнее graph/finalization failures, как в Form.batch. Исключение валидатора останавливает проход и передаётся после finalization; полностью проверенное состояние не обещается. Нет async callbacks/validators и rollback. Удаление узлов освобождает engine links, но пользовательские descriptors/closures с прямыми ссылками сами могут удерживать узлы; dispose не стирает ссылки приложения.

## Чистота и граница совместимости

Graph-enabled validators синхронно возвращают boolean/string без изменения raw/clean values, состава, options, baseline, touched и errors, включая другие поля. Только engine применяет validation metadata target. Во время прохода graph validation охранять точки библиотечных мутаций и отклонять запись до её применения (предлагаемый ValidationMutationError); нельзя создавать feedback loop повторными проходами. Рекомендуются readonly helper views/type tests. Произвольные внешние in-place JS writes нельзя полностью обнаружить без proxies; они запрещены контрактом, но полный перехват не обещается. Proxy-based dependency discovery/mutation tracking нет.

Формы без dependsOn или без явной активации сохраняют scheduling 2.2.0, callbacks, constructor behavior, payload, reset, touched и commitBaseline. Opt-in явно принимает selective automatic validation, полноту declared context и чистоту. Потенциально мутирующие legacy-валидаторы не мигрируются молча. Активация не валидирует и не меняет errors/flags. Пустой граф использует legacy scheduling. Изменения dependency options через поддерживаемые setters инвалидируют/пересобирают граф; dependency config коллекций в v1 задаётся при конструировании, поскольку options сегодня не writable публично. Перехват произвольной замены свойства Form не добавляется.

## Альтернативы и решения владельца перед HF-013

| Подход | Преимущество | Цена / вывод |
| --- | --- | --- |
| Tuple paths + прямые ссылки (основной) | Явные позиция/объект; буквальные точки; нет рекурсивного TS-взрыва | Runtime-проверка путей; ссылки могут удерживать узлы; явная активация корня |
| Только dot strings | Знакомый синтаксис error paths | Escaping, неоднозначные числа, случайная перепривязка позиции; не рекомендуется |
| Стабильные ID как сохраняемые пути | Удобные внешние ссылки | Runtime ID не являются durable domain keys; нужен отдельный lookup/lifetime contract |
| Типизированные selector functions | Удобный доступ к свойствам TypeScript | Риск скрытых чтений/эффектов; допустимы только как явные ref builders без tracking |
| Один root registry validator descriptors | Ясный lifecycle и общая конфигурация | Больше миграция с field options; возможная будущая альтернатива |
| Проверять всё / динамические Proxy reads | Простой fallback / меньше деклараций | Полная проверка явно сохранена; Proxy tracking исключён |

Владелец должен утвердить: (1) явную активацию/disposal и отклонение пересекающихся корней; (2) зависимости всего узла, grammar путей и позицию/direct ref; (3) ошибки missing-node/cycle, восстановление invalid graph и ограничение isValid; (4) инвалидацию по cleaned values/структуре и suppression rules; (5) отклонение мутаций opt-in validators, приоритет исключений и только sync; (6) стабильный порядок и консервативное транзитивное замыкание; (7) точные readonly ref types и declaration compatibility. Это предложения, не записи принятых решений DECISIONS.

План приёмки HF-013: declaration consumers ESM/CJS; legacy parity без деклараций; цепочки/ромбы/несвязные компоненты; self/multi-node/structural cycles; local/root/literal-dot/index paths; equal-valued reorder и полная замена; удаление target/source и missing refs; duplicate requests/nested batch/false writes/exception recovery; работа без подписчиков; отсутствие raw values в diagnostics; детерминированный dispose/link cleanup; отклонение мутаций из validators; atomic snapshots/reentrant writes; точные counts selective validation и profiling относительно STAB-02. Реализацию не начинать до решений владельца.
