## Контракт и переход с 2.1.1

- Существующие class-based Form/Field не требуют миграции. `isTouched`, синхронная валидация вне batch, `isValid`, `reset()`, сериализация и необязательный `adaptform/luxon` сохранены.
- `commitBaseline()` фиксирует очищенные значения для сравнения dirty, **не** меняет defaults для `reset()`. Поэтому после сброса `isDirty` может остаться `true`.
- Snapshots — независимые неизменяемые описания данных; Date, Map, Set, двоичные значения и пользовательские классы не обязательно представлены первоначальными объектами.
- `Form.batch()` откладывает **автоматическую** валидацию и уведомления; явный `checkValid()` выполняется сразу. Callback только синхронный, отката успешных присваиваний при исключении нет.
- Прямые изменения прежних массивов/options, объектов и произвольная замена свойств формы не всегда наблюдаются автоматически. Пользуйтесь штатными операциями и повторным чтением snapshot.
- Перед отправкой нужна явная валидация: `toJSON()` сам не проверяет форму. См. [примеры](../../ai/HEADLESS_STATE_USAGE.ru.md), [контракт](../../ai/HEADLESS_STATE_CONTRACT.ru.md), [changelog](../../../CHANGELOG.ru.md).

## Состав публикуемого пакета

- `package.json`, `package-lock.json.version` и `package-lock.json.packages[""].version` должны иметь версию **2.2.0**.
- Сохраняются точки входа `.` и `./luxon` (ESM, CJS, .d.ts), необязательный peer Luxon, allowlist пакета и отсутствие новых обязательных зависимостей.
- README, changelog, примеры, решения и релизная документация согласованы на EN/RU. Отмечать дистрибутив опубликованным **только после** успешного workflow и проверки точной версии в npm (для 2.2.0 выполнено).
- Не изменять workflow GitHub Actions для npm, ключи и `NPM_PUBLISH_ENABLED`.

**Версия 2.2.0 успешно опубликована через отдельно согласованный автоматический workflow. Это не разрешение на теги, GitHub Release или не согласованные изменения кода в дальнейшем.** [Workflow публикации](../../NPM_PUBLISH.ru.md) может автоматически публиковать новую версию только при `NPM_PUBLISH_ENABLED=true` после успешного CI в master; ранее он пропускался. После merge нужно проверить реальный итог workflow, а не делать вывод о постоянном состоянии настройки. Существующие Git-ветки сохранять.
