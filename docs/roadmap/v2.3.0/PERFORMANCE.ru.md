Измерено 2026-10-21 в `feature/v2.3.0-performance` от master `7d9a13bfd9578e0119a59cc4550b305906fe1e39` (принятая foundation PR #25). Коммит кода и тестов: `6fd81ccb2fd264cf45b5290724735a1541f24639`. Версия пакета остаётся **2.2.0**; публичный API, зависимости, валидация, reset, сериализация и идентичность коллекций не меняются. Слияние, публикация, релиз, теги и удаление веток не выполнялись.

## Доказательства и причины

Неизменённый [стенд](../../../scripts/benchmark-headless.mjs) использует собранный ESM. Полные медианы/min/max семи выборок, число итераций и GC-выборки: [до](benchmark-performance-before.json), [после](benchmark-performance-after.json). Оба отчёта используют одинаковую среду: Linux 6.18.55 x64, Intel Xeon Platinum 8370C (3 доступных CPU), Node 24.19.0 / V8 13.6.233.17-node.51. Пять прогревов, семь выборок, цель 25 мс, максимум 100 итераций на выборку; накладные расходы таймера включены, подготовка/очистка объектов исключены. Add/remove — пара: добавление без валидации, затем удаление с прежней полной автоматической валидацией. Параллельные команды проверок во время этих замеров не запускались; хост общий. Прежние 4,84/5,82/245 мс получены в другом запуске/на другом CPU и не используются как знаменатель этого сравнения.

Отдельный исходный запуск с CPU-профилем выявил горячие функции по собственным сэмплам: `reconcile` (4477), `freezeSnapshot` (2175), поиск `_fields` (1981), `equalValue` (1316). Числа относятся ко всему смешанному стенду, а не к процентам или отдельному сценарию; исходные временные замеры выше повторены без профилирования.

- Каждая валидация дочернего узла распространяла `changed()` по предкам и заново строила их множества детей. Валидация N детей повторно обходила N соседей, приближая затраты наблюдаемых коллекций к квадратичным.
- Неизменённое чтение повторно захватывало значения, ошибки, метаданные и потомков, затем рекурсивно замораживало и структурно сравнивало новый граф. Стабильная ссылка сама по себе не устраняла повторный захват.
- При захвате Form отдельные агрегирующие getters повторно искали поля. Вложенный захват и flush повторяли обновление детей и заморозку уже неизменяемых поддеревьев.

## Оптимизации

- Локальная сверка состава отделена от инвалидации предков. Прямые структурные мутации по-прежнему сразу сверяют связи, включая удаление внутри batch; subscribe/unsubscribe и публичное чтение также сверяют владение.
- Добавлены признак инвалидации и единая эпоха проверки на публичное чтение/волну flush. Каждый достижимый store обновляется один раз за волну; равное состояние сохраняет ссылку snapshot, после обновления уведомления выбираются сравнением ссылок.
- Повторно используются snapshots скалярных Field и неизменённые агрегаты Form/коллекций по ссылкам дочерних snapshots, метаданным, ошибкам и упорядоченным ID коллекций. Поиск полей кешируется только на время одного захвата Form, с очисткой в `finally`.
- Слабый реестр рекурсивно замороженных snapshots исключает повторную заморозку неизменяемых поддеревьев движка; поверхностная заморозка пользовательского объекта не считается глубокой.
- Сохранены проверки внешних изменений значений/ошибок/legacy-массивов, замены/добавления/удаления свойств, mutable Date/Map/Set/циклических значений и пользовательских getters/переопределений capture. Публичное чтение и финализация мутации проверяют потомков; кеш агрегатов не обходит пользовательские производные getters. Proxy, граф зависимостей, переработка планировщика и публичный API кеша не добавлены.

## Оставшиеся ограничения и компромиссы

- Неизменённое публичное чтение корня по-прежнему проверяет потомков за O(N), сохраняя обнаружение произвольных внешних изменений. Mutable-структуры требуют захвата/сравнения. O(1) для snapshots не обещается.
- Удаление из коллекции по-прежнему валидирует каждого оставшегося ребёнка, сохраняя число вызовов и контекст. Агрегирование dirty/содержимого и изменённых snapshots зависит от объёма поддерживаемого содержимого/глубины; выборочная валидация и движок зависимостей не добавлены.
- Слабые кеши увеличивают расходы памяти. Шесть heap-выборок после GC до: **11 604 088–11 661 480 байт** (первая → последняя 11 604 088 → 11 650 472); после: **14 050 648–14 085 472 байт** (14 050 648 → 14 085 472). Более высокий heap после прогрева — наблюдаемый компромисс, а не установленная причина удержания объектов/утечки. Короткая фиксированная GC-нагрузка не доказывает отсутствие утечек и не представляет все сценарии потребителей.
- Время на общем хосте варьируется; диапазоны сохранены, небольшие изменения (особенно записи без подписки) неубедительны. Пороги времени в CI и универсальные гарантии задержек не вводятся. Пользовательские getters/capture намеренно используют совместимый путь захвата и могут получить меньшее ускорение.
